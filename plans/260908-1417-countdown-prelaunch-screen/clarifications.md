# Clarifications — Countdown Prelaunch Screen (MoMorph 8PJQswPZmU)

Screen: https://momorph.ai/files/9ypp4enmFmdK3YAFJLIu6C/screens/8PJQswPZmU

## Session 2026-09-08

- Q: Spec says navigation to other pages is locked while the countdown hasn't hit zero, unlocked once it does — site-wide gate, or standalone page? → A: Site-wide gate. Middleware redirects ALL routes to `/countdown` while active; the whole app unlocks once inactive.
- Q: Spec has a literal TODO for a new API endpoint to supply the target datetime, but the home screen's hero countdown already reads `EVENT_DATETIME` from an env var. Which source? → A: Reuse `EVENT_DATETIME`. No new API endpoint. Same source of truth as the home screen.
- Q: Access-control test cases are explicitly non-committal ("as per application configuration"). What's the actual rule? → A: Fully public, no auth check — the gate has to block guests too (a guest can't be asked to log in to a page that exists because the app itself isn't open).
- Q: `.env.local` already has `EVENT_DATETIME` set to a future date — building the gate as a pure `EVENT_DATETIME`-vs-now check would immediately lock the entire app (including in dev/test) the moment this ships, breaking all three existing E2E suites. How should the gate be controlled? → A: A **separate** toggle env var, `PRELAUNCH_GATE_ENABLED` (default `false`/unset = off), independent of `EVENT_DATETIME`. The gate is active only when explicitly turned on. Existing screens and their E2E suites are unaffected by default.

## Architecture decisions (resolved without asking, non-blocking)

- **Gate is a pure on/off toggle, not date-computed.** `PRELAUNCH_GATE_ENABLED=true` gates everything unconditionally (except `/countdown` itself and Next internals); it does NOT compare against `EVENT_DATETIME`. This avoids middleware (Edge Runtime) needing to read/compute against `EVENT_DATETIME` at all, sidestepping the exact "env var frozen empty in the Docker-built Edge Runtime bundle" class of bug already hit and fixed twice this project for the Supabase vars (see `plans/reports/260908-docker-build-guard/`). Ops flips the toggle on before a real prelaunch period and off once the event goes live — a manual, deliberate operation, not automatic.
- **`PRELAUNCH_GATE_ENABLED` still needs Docker build-arg wiring** (`ARG`/`ENV` in the Dockerfile, mirroring the existing `NEXT_PUBLIC_SUPABASE_URL` pattern) because it's read inside `middleware.ts`, which runs in the Edge Runtime and is subject to the same build-time-freezing behavior — this is NOT limited to `NEXT_PUBLIC_`-prefixed vars, it applies to anything middleware reads. This is the single most important lesson from the recent Docker debugging sessions, applied proactively here.
- **Route:** `/countdown`.
- **Middleware matcher broadened to a catch-all** (`/((?!_next/static|_next/image|favicon.ico|api).*)`) instead of the current explicit per-route list. This is a deliberate improvement: every prior plan (home, award-information) had to remember to add its new route to the matcher's explicit array — a broad catch-all removes that recurring maintenance chore and guarantees the prelaunch gate actually covers every route, including ones added later.
- **Countdown display cadence:** this screen's spec explicitly says "auto-updates every second" (unlike the home screen's hero countdown, which ticks every ~30s since its spec only required minute-granularity). Honor the stricter spec for this screen specifically — do not force the two screens to share one hook/interval.
- **Gate logic split for testability:** the gate's routing decision is extracted as a small pure function (e.g. `shouldGate(pathname, enabled)`), unit-tested directly (Jest) — not E2E-tested for the gate-ON scenario, since flipping a real env var mid-suite would require a second Playwright server/config for one boolean. The E2E suite (`e2e/countdown.spec.ts`) covers the `/countdown` page's own content/rendering, plus a regression check that existing routes are NOT redirected when the gate is off (the safe default) — see phase-t-red for the exact split.
- **No bypass for admins.** Not requested; the gate applies uniformly to everyone, matching the test cases' "access allowed or blocked, as per application configuration" being resolved uniformly, not per-role.
